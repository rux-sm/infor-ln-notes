Session Summary

Sales and Production Orders

Why some warehousing steps are manual and others automatic, a routing validation that finds a BOM loop, and a clean material-issue run to learn from.

Session Date2026-08-11
TypeTraining Session
Orientation only. This is the shareable half of a longer internal record. It carries no citations, and nothing here should be relied on for implementation work without checking it against official Infor documentation.

What this covered

Review of an earlier Ship from Stock exercise, an explanation of why some warehousing steps are manual and others automatic, and a fresh production-order exercise — item, BOM, routing, order creation, release, and material issue — followed by a discussion of what to study next.

Topics

Ship from Stock, confirmed working

The earlier shipment of item 9010-2010 was checked against inventory and confirmed correct.

What was shown:

  1. Warehouse - Item Inventory whwmd2515m000 — starting position: On Hand 966, On Order 60, Allocated 210, Blocked 0, Economic Stock 816.
  2. Inventory Transactions whinr1510m000 — after the shipment, an Issue transaction of 5.000 and Inventory After Transaction 961.000.
  3. 966 − 961 = 5 — exactly the shipped quantity. The shipment worked as it should.

Why some warehousing steps are manual and others aren't

Whether a step (generating advice, picking, confirming a shipment) runs by itself or needs someone to click it comes from the procedure attached to the order's type, configured in Activities by Procedure whinh0106m000 — an Automatic setting per activity. It's a configuration choice, not a fixed rule of the software; different order types can behave completely differently.

The learning method: trace, don't memorize

When a field defaults to a value you didn't expect, the trainer's advice was to trace it back to where it actually comes from — the item master, business-partner data, order type, sales user profile — using the session's own Help control, rather than guessing or memorizing "it's always X." No single default source was actually pinned down in this session; these were framed as questions to go investigate, not answers.

One of them now has an answer: a sales order's order type defaults from the customer record, and if the customer has none set, falls back to the current user's sales profile.

A real BOM validation failure

What was shown:

  1. Built or reviewed item 9010-2010, its job-shop BOM, and its routing.
  2. Ran Validate Job Shop Routing from Job Shop Routings tirou4100m000 for routing 0, revision 000001.
  3. The report came back "Loop found in Multilevel BOM", with the loop path shown.

This is a genuine, learnable validation failure — worth recognizing if you hit it again, though exactly what LN checks to produce it isn't documented anywhere available yet.

The recording also showed Approve Revision, Use for Planning, and Use for Costing actions on the BOM/routing records. These are real: only one BOM (and one routing) per item and site can be "used for planning" at a time, and only one per product can be "used for costing" — the check box picks the winner when more than one candidate exists.

A clean, complete material-issue run

Unlike the earlier (2026-08-06) session's mistaken attempt, this run went cleanly end to end:

  1. Production Order tisfc0101m100 — order 010000744 for item 9010-2010, quantity 1; BOM JB0000238 rev 000002, routing 0 rev 000001, warehouse ADNA02 RAW MATERIALS, two operations; status Created.
  2. Release Orders run from Production Orders tisfc0501m000 — this is literally what "release to the job shop" means; it's also what changes the order's status to Released.
  3. Material to Issue for Production Orders ticst0101m100 — material 100400 showed Estimated 2.000, Actual Qty 0.000, To Issue by Warehouse 2.000 after release.
  4. Warehousing Orders whinh2100m000 showed a planned production receipt and an open production issue for the order. The issue's detail whinh2100m100 showed order type 30 — Production (Out), source ADNA02 RAW MATERIALS, destination work center A1000.
  5. Outbound Line Status Overview whinh2129m000 — ordered quantity 2, with Generate Outbound Advice and Release Outbound Advice both unfinished and non-automatic. Both were then run manually. (This is controlled by settings on the material line that decide whether the warehouse side kicks off automatically on release or needs a manual push — consistent with what was seen here, though which exact setting this environment uses wasn't pinned down.)
  6. The issue order reached Shipped, ordered/advised quantity 2. Back in ticst0101m100: production order Active, Actual Qty 2.000, To Issue by Warehouse 0. (Active specifically means a real transaction — like this material issue — has happened against the order.)

This is the version to learn the material-issue flow from — the earlier session's version is not.

Completion left for later

The remaining steps — completing the operations, receiving the finished item through the receipt warehousing order, and reporting the production order complete — were assigned as follow-up, not demonstrated live. Report Operations Completed tisfc0130m000 records production progress, and its Quantity Delivered field is the finished-goods quantity posted to inventory, same as seen in the 2026-08-06 session.

What's next: planning before subcontracting

The group chose to walk through planning next, before touching subcontracting — subcontracting needs more setup and the available trainer had less recent experience with it. The Default Supply Source field on the item record tcibd0501m100 determines an item's default supply method when on-hand is insufficient, which is where the planning discussion picked up.

What was decided

  1. Walk through planning end-to-end before starting subcontracting training.
  2. Teach execution (running orders) and planning as two separate learning blocks for now.
  3. Finish the in-progress production-order exercise (completion and receipt) after this meeting, rather than treating it as done.

Key takeaways

  • Manual-vs-automatic warehousing behavior comes from the order type's configured procedure — always check that before assuming a step is "supposed to" require a click.
  • When a default looks wrong or surprising, trace it to its source instead of guessing — sales order type, for example, traces to the customer record, then the user's sales profile.
  • Only one BOM (and one routing) per item/site can be "used for planning" or "used for costing" at a time.
  • "Loop found in Multilevel BOM" is a real, learnable validation error — not a bug.
  • A production order becomes Active the moment a real transaction (like a material issue) happens against it, not just from being released.
  • The material-issue run in *this* session (order 010000744) is the clean example to learn from; the 2026-08-06 session's version is not.
  • Planning is the next topic to study; subcontracting is deferred.
